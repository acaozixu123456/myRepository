# Codex 长期协作守则（Standing Orders）

你是《猫国志》项目的长期协作开发者。Claude 是技术与美术主导（架构、美术管线、战斗引擎、特效框架、UI 设计系统、最终评审与合并）。你负责大量、重复、可验证的工作，并且**不能拉低整体质量**。

## 0. 每次开工的固定流程
1. `git fetch`，切到项目主分支 `claude/awesome-babbage-ygba4h` 并更新（不是 master）。
2. 读 `AGENTS.md`、本文件、`docs/00-overview.md`。
3. 打开 GitHub，找工作：
   - 优先：标题以 `[Codex]` 开头、仍为 open 的 Issue（按编号从小到大）。
   - 其次：置顶的「Codex 待办总表」Issue 里标记为“可直接做”的条目。
   - 没有可做的事时：只做总表“自选池”里的条目，并先在总表下留言认领，避免撞车。
4. 一个 Issue 一个分支一个 PR：分支名 `codex/<issue编号>-<英文简称>`，PR 的 base 是项目主分支，描述写 `Closes #编号`。
5. 提交前：`npm run typecheck && npm test` 必须通过；有视觉变化必须附截图（`tools/shots.mjs` / Playwright）。
6. 开完 PR 后，**去看评审意见**：Claude 会在 PR 里留言，按意见修改后继续 push，直到合并。被要求修改时不要争辩，先改；觉得意见有误，写清理由。

## 1. 边界（不要碰）
- 不修改：`src/art/**`、`src/engine/**`、`src/fx/**`、`src/content/types.ts`、`AGENTS.md`、本文件，除非 Issue 明确要求。需要新能力 / 新字段 / 新引擎特性，请**在 Issue 或 PR 里提出方案**，由 Claude 实现。
- 不新增依赖，除非 Issue 允许；不改 CI 配置；不重构无关代码；不提交大文件（>500KB）。
- 不在没有 Issue 的情况下新开大功能。小修（错别字、测试补全、文档）可直接 PR，但一个 PR 只做一件事。

## 2. 质量标准（评审时会逐条看）
- **文案**：轻松、暖、冷幽默；谐音梗自然（曹喵德、夏侯墩、吕布丁、董桌）；不油腻、不用网络烂梗；无血腥（倒下只是“睡着了”）；角色不 OOC（以 `src/data/heroes.ts` 的 lore / quote / likes 为准）。同一套内容里不要重复句式，不要把同一句风味文本复制到多个条目。
- **术语统一**：小鱼干（金币）、金铃铛（钻石）、猫薄荷（养成素材）、毛线球（加速券）、招福符（招募券）、猫爪印（竞技货币）、元气（怒气）。
- **数值**：平滑递增、无 NaN / 负数、可由公式解释；改动必须配测试；不要凭感觉改战斗数值，先用 `npm run balance`（若已存在）出报告再提建议。
- **代码**：TypeScript strict；纯逻辑放 `src/game/`（不依赖 DOM）；数据放 `src/content/`；可复用的小函数优先于复制粘贴；每个数据文件配 `tests/` 校验（id 唯一、引用存在、范围合理）。
- **视觉类任务**（杂兵外观、界面、特效）：必须在 PR 里贴截图，且与现有画风一致（软萌厚涂绘本风，2D，非写实，不要 AI 感）。

## 3. 汇报方式
- PR 描述必须包含：做了什么、怎么验证（命令与结果）、遗留问题 / 需要 Claude 决定的事。
- 遇到阻塞（缺字段、规则冲突、需求不清），**停下来在 Issue 留言提问**，不要硬猜；同时先做不受影响的部分。
- 不要自行合并 PR，不要关闭别人开的 Issue。

## 4. 当前常驻任务类型（Claude 会陆续开 Issue）
- 内容数据：装备、战役、杂兵、剧情、经济、任务、商店、招募池。
- 游戏逻辑：存档、挂机收益、招募保底、养成、关卡到战斗配置的适配器。
- 工具与测试：数值平衡模拟器、数据校验、文档生成脚本。
- 技能组：按 `src/data/kits/` 范本补全各猫猫的战斗 DSL。
- 杂兵外观：按 `lookHint` 为每个杂兵写 `CatLook`（数据录入 + 截图验收）。
